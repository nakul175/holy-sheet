# Administrator-managed custom collection foundation (HOLY-39)

Native service reached through the collections route. Current verified central tenant administrator status plus an explicit manage-collections tenant grant are required; the new grant registry is empty in live environments. Collection ownership, creating metadata or configuring fields grants no record/field/schema permissions. Other-owner assignment additionally needs a qualified current owner-directory adapter and active native membership in a reviewed tenant workspace. No production owner adapter or grant-management UI is supplied.

Actor-private ten-minute previews bind immutable UUID, unique normalized 1–100-character name, description, owner, expected collection/schema/proof revisions and validated initial field IDs/types/defaults. At most 200 custom collections and 100 initial fields are supported. Initial schema reuses the existing schema validator; no guessed reference defaults or weaker custom-record path. Apply commits collection/settings, initial field/schema versions, immutable collection history, operation ledger and metadata audit atomically; concurrent retries create once. Only hashes/proof/version metadata are retained in pending previews. Current owner proof and configuration grant are rechecked before commit.

Rename preserves immutable collection IDs and existing API references. Deprecation hides new choices and forbids native/API/import/template creation, while ordinary current permissions continue to govern reads/edits/history of existing records. Record template choices hide for deprecated collections. Standard core collections cannot be changed through this custom workflow. Existing records use the same required/typed/unique fields, lifecycle, references, audit and native APIs. Connected API clients additionally need an explicit record-api-v1 consumer registration for the stable custom collection ID; a user grant alone does not opt an app in. Query/detail/update/history/references/change polling use that same fence. No consumer registration is seeded.

Removal requires a separately qualified complete dependency inventory, even if local tables are empty. Records including Trash, fields, views, templates, transfer jobs and registered app consumers block with generic impact; hidden dependency names/IDs/counts are not exposed. Final inspection and local dependency checks run under the native tenant lock. Only an empty custom collection can be removed, retaining its non-reusable identity/history tombstone; no data purge, cascade or schedule runs. No production dependency inventory adapter is supplied.

Tests cover dual administration checks, no implicit grants, native required/unique validation, rename/deprecation preservation, owner proof failure/revocation, name/version/retry, current metadata visibility, actor-private previews, grant removal before apply, generic dependency impact, complete inventory gate, removal tombstones/immutability, stale removal and shared schema validation. Required CI includes actual PostgreSQL concurrent collection/schema creation with zero automatic grants plus full regression/accessibility/container/backup-restore gates.

## Connected in this change

`GET/POST /api/v1/workspaces/:id/tenants/:tenantId/collections` calls `SharedRecordCollectionRepository` through the same suite-tenant authority as records, permissions, schema, saved views, lifecycle, merge, import, export, history and the record client (`authenticateRecordAuthority` and `HS_RECORDS_ENABLED`). There is no JWT-role fallback and no tenant-provisioning adapter. Each request constructs the repository with the verified authority only. No `CollectionOwnerAuthority` or `CollectionDependencyAuthority` is supplied, so assigning another owner fails closed with `record_collection_owner_unavailable` and every removal fails closed with `record_collection_inventory_unavailable`.

`GET` lists collections visible to the verified actor. `includeDeprecated=1` includes deprecated collections that actor may already see. Any other query is rejected. `POST` accepts one command. `kind: preview` stores an actor-private review of a create, rename or deprecation proposal. `kind: apply` requires `confirm: save-custom-collection`, the review hash and an operation id, and commits that change atomically. `kind: preview-removal` names the custom collection id and expected version. `kind: remove` requires `confirm: remove-empty-custom-collection`. The transport kind is not passed into the repository. Responses are `no-store` and vary on cookie and authorization.

A missing flag, failed suite proof, missing tenant-administrator status, missing `manage-collections` grant, cross-origin write, forged field or unexpected failure is rejected. Apply after the grant disappears does not leave a collection row. Another administrator cannot apply a preview they did not create, and the pending preview retains only hashes. Removal of a non-empty collection and of a core collection stays refused. An empty custom collection still leaves its identity and history tombstone when a qualified inventory adapter is present. This connection does not supply that adapter, a grant-management UI or a collection editor, and it does not mark HOLY-39 Done.

Remaining full story: native accessible collection/schema editor and confirmation UX, reviewed live tenant/grant/owner/dependency adapters, app opt-in/consumer registration and representative performance/fault acceptance. No live collection, schema, grant or ownership change is seeded; no full HOLY-39 completion is claimed.
