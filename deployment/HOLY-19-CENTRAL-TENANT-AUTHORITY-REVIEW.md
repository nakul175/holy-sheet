# Central tenant authority adapter — prepared, not deployed

HOLY-19 through HOLY-29 and the later structured-record configuration stories require current suite tenant authority. Native workspace administration, email matching, a global `super_admin` claim and Directory `AdminScope.allowed_roles` do not establish that authority. Inspection of the actual Directory control code confirms that AdminScope delegates which resource roles may be assigned to another user.

This batch prepares an Accounts-side read-only adapter and a proposed explicit Directory `TenantAdministrator` model/migration. It changes no live source, database, identity, mapping, role or flag. There is no HTTP/native record activation, and no full story acceptance claim.

The proposed `/internal/tenant/status` route authenticates only the existing `holy-sheet` confidential client. It reuses Accounts' existing provider Session, client Grant, enabled account/link, SourceSession binding and current upstream SHO session checks. It verifies the upstream session before and after the Directory read. The response is bound to the exact verified subject, tenant and workspace. A final Directory revision check rejects authority changes during the upstream round trip. Secrets and session UIDs appear only in the authenticated POST body, never response JSON, URLs or logs.

Directory proof requires all of: an exact issuer/subject-to-person binding; active person; existing organisation; active organisation membership; active Holy Sheet application access; a reviewed mapping of this exact workspace to that organisation; a central connector with verified permission/revocation cutover and a restore-verified baseline. The adapter is explicitly disabled by default. It opens only an explicitly configured absolute SQLite path with `readOnly:true` and query-only transactions; a missing database or schema is unavailable and is never created automatically. No email or role aliases are resolved.

Tenant administration requires an additional active, reviewed, versioned `TenantAdministrator` row for the same person, organisation and `holy-sheet` application. The migration creates the empty table only; the model defaults new rows to inactive. This proof never grants native collection, record or sensitive-field capabilities. Existing HS repository transactions must still require those independent permissions and compare authority revisions before commit.

`integrations/central/prepare-patches.py` prepares review patches against the previously verified exact Accounts app and Directory models source hashes. It refuses changed source and an already-used migration name. It does not edit or execute deployed source. The Accounts patch factors the existing session check into a private shared function while preserving its checks. The new module is built by `npm run build:tenant-authority`; source/module SHA-256 provenance is written alongside it under `artifacts/central-tenant-authority/`.

Validation in this batch:

- The actual Directory Django 5.2.18 models and existing migrations were copied into a disposable local fixture, combined with the proposed model/migration, checked with `makemigrations --check --dry-run`, then migrated. The resulting synthetic SQL and its source/migration/model hashes are stored in `integrations/central/fixtures/`. No deployed Directory database was read. The generator requires an explicit source/output and verifies the known model hash.
- Adapter tests use that Django-generated fixture and verify each gate, wrong tenant/subject/workspace denial, no inferred admin, explicit admin activation/revocation, missing schema/read-only behavior, request authentication, source-session revocation, mid-request authority changes, generic errors and the compiled portable module's behavior/provenance.
- The existing 17 Accounts login, PKCE, source-revocation, encrypted-adapter and logout regressions passed against an isolated local copy with the prepared Accounts patch and portable module. They used synthetic keys/databases and loopback servers, not live accounts. They do not prove a live Holy Sheet tenant endpoint exchange.

Before any staging activation: review the exact central role/schema mapping and tenant retention policy; verify current Accounts/Directory source hashes and rebase if changed; prepare backups/rollback; apply the reviewed model/migration and module/route changes with the endpoint flag off; configure the actual Directory path privately; qualify the central connector cutover; obtain specific approval for any real tenant/subject/workspace/admin mappings; then enable only the intended test environment. Copying the prepared patches is not deployment acceptance. Never set fake parity/revocation timestamps or restore evidence to unlock the route.

Still required: the HS server-side verified-session client and native record host/UI, approved real authority data, authenticated account matrix, live revocation/race/logout qualification, and the remaining individual story acceptance gates. No signing-key access, session fabrication, QA password reset, broad admin grant, purge schedule or production rollout is part of this batch.
