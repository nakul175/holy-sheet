# Shared-record tenant, transaction and field-access foundation

This candidate adds an unexposed service/model foundation for HOLY-19 through HOLY-21. It does not activate shared-record CRUD, provision a tenant or populate live grants. A mandatory `CurrentSuiteTenantAuthority` must verify the exact current suite subject, tenant and reviewed workspace mapping before and after a transaction. There is no production adapter, JWT-role/email fallback or workspace-as-tenant inference. The local directory's mapping tables were empty; this candidate does not invent one. Existing HS native active workspace membership is also required, and explicit native collection/record capabilities remain separate from workspace administration.

Suite tenant IDs and business Organisation record IDs are separate namespaces and meanings. Five standard collections are distinct; immutable records are tenant-owned and may be read through another explicitly mapped workspace under current authority. Account parents must be exactly one same-tenant Organisation. Contracts require one or more same-tenant legal Organisations, may cover multiple Accounts, and deferred database constraints prevent a last legal-party removal. Stable IDs/tenant/type and relationship endpoints are guarded at the database boundary. No staff association or record/document relation grants application membership or page access.

Typed inputs validate trimmed 1–200 Unicode-character names, known field keys, URL protocols, email/phone/date/boolean/select/number and exact minor-unit currency representations. Currency codes are format-validated without conversion or exchange-rate claims. Names are indexed independently of document bodies. Sensitive contact/employee/contract fields require separate current view/write/history flags. Partial edits preserve hidden fields; detail, list and history omit protected values. Search/filter/order currently support only permitted record names, not sensitive-value predicates. Unknown/deprecated fields cannot be edited. Attachment/custom record-reference writes remain unavailable without their current reference authority; no adapter is supplied or claimed.

Creates and updates use tenant/actor-bound UUID operation ledgers. Edits require record and schema versions; an old successful retry reports both applied and current versions truthfully. Record change, operation, protected history event and metadata-only outbox event commit atomically. Revoked/unavailable suite authority before commit rolls them all back. Ordinary audit/outbox metadata contains IDs/versions, not private names/values. Outbox delivery is not enabled. Sensitive classification changes, full historical schema provenance, 50-event history cursors and value restoration remain later work; this is not full HOLY-28/29 completion.

Queries return at most 50 permitted records using stable name/ID keysets and actor/tenant/workspace/query-bound random cursors, expiring after five minutes. Literal wildcard escaping and current rights are checked server-side. Existing explicit operator-invoked maintenance removes expired cursor metadata; no scheduler is created. PostgreSQL CI seeds 100,000 synthetic records, verifies two fifty-item pages without duplicate IDs and preserves the actual query's execution plan/index evidence and timings. These measurements are not an approved p95/load budget or live-tenant performance claim.

Document links recheck independent HS page access and reviewed same-tenant workspace mapping. Record readers cannot obtain an inaccessible page title or ID from the relation. Linking changes no page grants. Exact unique typed values reject conflicting writes without returning a matching record ID. Schema/custom-collection administration, general relationship edit/reparent previews, archive/Trash/merge/import/export, native permission-management UI, deployed tenant mapping, structured-record UI and real suite adapter qualification remain open. No story is marked Done from this foundation.

Migration 020 is additive and its registries are empty by default. Application rollback keeps those unused tables. Synthetic local/CI fixtures are isolated and do not represent production provisioning. No users, credentials, tenant memberships, permissions, schedules or purge jobs are created by this release.
