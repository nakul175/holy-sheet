# Versioned record layout foundation and renderer (HOLY-40)

The record-layouts route exposes draft, preview and publish to the approved suite-tenant authority, and the records screen hosts the published layout. Current central tenant administrator plus collection schema/view capability manages layouts; no permission is created by arranging a field. Drafts and published pointers are separate, optimistic and operation-idempotent. Immutable layout/publication versions retain actor/time/source metadata; no record values are stored or rewritten.

Layouts reference stable field IDs in at most ten tabs, twenty sections and 110 distinct slots with one/two-column metadata and bounded plain labels/descriptions. Drafts may be incomplete for editing. Exact ten-minute publication previews require name and every active required field in an editable reachable position, current field visibility and current schema/policy/proof. Stale drafts/schema/permissions or final-proof expiry roll publication back. Both active draft and published fields register generic view dependencies, preserving compatibility with migration replays. A schema field must first be optional and placed in the published editable layout before becoming required.

Current reads filter inaccessible/deprecated fields and empty sections/tabs, with current write flags and no values/defaults. Record-level view permission can open the layout without granting collection-wide access. Field rename preserves positions; field deprecation is blocked while active layout dependencies exist. A current schema/layout mismatch disables creation until review.

The reusable React renderer has labelled controls, keyboard Arrow/Home/End tabs, preserved mounted panels, visible focus, 44-pixel controls and a single-column phone layout. A new publication announces availability but does not replace an open form's layout; switching is disabled while unsaved changes exist. Current field revocation removes controls immediately, and actor/record scope changes remount layout state. Host field values must be controlled by the authoritative form draft and the existing session/permission boundary; this renderer is not a substitute for that host.

A synthetic local-only qualification route exists only when HS_LOCAL_PREVIEW=1 and returns 404 otherwise. No business data is persisted there; no production preview flag is enabled. Browser checks at 1100/390 px verify keyboard tabs, exact label/read-only behavior, preservation through publication, phone geometry/no overflow and zero axe WCAG A/AA violations. Service tests cover draft/publication separation, rights, required reachability, sensitivity, schema impacts, retry/stale/expiry, immutable evidence and actual startup migration replay. CI adds real PostgreSQL publication retries/replay, full regression and container gates.

## Connected in this change

`GET/POST /api/v1/workspaces/:id/tenants/:tenantId/record-layouts` calls `SharedRecordLayoutRepository` through the same suite-tenant authority as records, permissions, schema, saved views, lifecycle, merge, import, export, history, the record client and custom collections (`authenticateRecordAuthority` and `HS_RECORDS_ENABLED`). There is no JWT-role fallback and no tenant-provisioning adapter. Each request constructs the repository with the verified authority only.

`GET ?collection=` returns the published layout for a caller who can view the collection. `recordId` opens that same published layout with record-level view permission and does not grant collection-wide access. `includeDraft=1` is the only read that returns the management draft, and it still requires the tenant administrator plus collection schema and view. Any other query is rejected. A missing flag, failed suite proof, cross-origin write, forged field or unexpected failure is rejected. Responses are `no-store` and vary on cookie and authorization.

`POST` accepts one command. `kind: save` stores a draft. `kind: preview` stores an actor-private publication review. `kind: publish` requires `confirm: publish-record-layout`, the review hash and an operation id. The transport kind is not passed into the repository. Draft and publish retries stay operation-idempotent. Publication still rolls back when the draft, schema, policy or proof is stale, or when the ten-minute review has expired. Required fields must be in an editable reachable slot. Layouts still do not store or rewrite record values.

The collection layout screen arranges stable field IDs into at most ten tabs, twenty sections and 110 slots, with one- or two-column sections and edit or read-only slots. Saving an incomplete section stays in the browser. The records screen renders the published layout with the existing field controls. The host keeps field values, the session boundary and create/edit permission; the renderer does not. A new publication is announced on an open form and does not replace it while unsaved changes exist. Fields absent from the published layout, or absent from the caller's field catalogue, are not shown. Creation stays paused when the published layout reports that it cannot accept a record. `HS_LOCAL_PREVIEW` remains the only switch for the synthetic qualification route, and no production preview flag is enabled.

Remaining full story: representative live-tenant fault and performance qualification beyond the existing local browser route and PostgreSQL publication replay. No full HOLY-40 completion is claimed.
